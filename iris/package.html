Tools to check the numbers from a language-model evaluation before you trust them and after a run. This applies to benchmark scores, LLM-as-judge scores and fine-tuning studies. IRIS recounts published evaluation studies from their own released output files, and this package puts the same checks in your hands for your own outputs. Your files are opened read-only and never changed. Reports go to a separate folder, and the checker refuses a folder inside the folder that holds an input, so run it from outside your data folder. The checker sends nothing anywhere. Two parts need other software or the network when you run them: parser-check/replycheck.py runs a model on your machine, and installing the Faults and Guards package from PyPI downloads it. Python 3.9 or later.

Before a run

  • Read the Guards before the work. Install the package with pip install faultsguards or from the wheel in faultsguards/, then run python -m faultsguards guards
  • Decide how each answer will be extracted from a reply and write that rule down before any reply exists.
  • If you fine-tune or compare systems, plan at least two runs of the same items with the same settings. The difference between those two runs is the repeat floor, and it is the first thing any later difference is read against.
  • Give the plan a check block: check-block/. The packs for language-model evaluations (L) and public copy (P) are in check-block/SPEC.md.

After a run

  • Save the outputs of each run as a JSONL file with one reply per line. Each line needs an item id, the reply, what your parser extracted and whether it was scored correct. Keep these files in one folder and write reports to a different folder.
  • Read a sample of replies beside what your parser extracted: python iris_check.py sample run1.jsonl --reply-field reply --extracted-field pred --label-field family --id-field id -n 10 --seed 1 This writes a reading sheet as HTML and CSV with 10 random replies per label. Read each reply. In the CSV, write x in the read column for every reply you read. In the misparsed column write x, bad, 1 or wrong where the extracted value is not the answer the reply gives. A parse that is fine takes ok, y, yes, 0, no, n, false, f or a blank. Any other entry is an error that names the row. Then run python iris_check.py sample --tally SHEET.csv, which prints the result for each label.
  • The tally rule, exactly: a label reads "cannot tell (not read)" if any of its rows is unread. Otherwise it reads "cannot tell (parser)" when more than 10% of its read rows are mis-parsed, so 1 of 10 is fine, 2 of 10 is not, and 1 of 9 is not. Otherwise the rate can be read. The default sample is 10 replies per label.
  • Reply text that starts with =, +, - or @ gets a single quote in front of it in the CSV, so a spreadsheet does not run it as a formula. Rows that lack the reply or extracted field, blank lines, and rows with a missing or null label (shown as (none)) are counted on the console and in the JSON report.
  • Count the flips between repeats of the same items: python iris_check.py repeat run1.jsonl run2.jsonl --id-field id --correct-field correct Item ids are turned into strings first, so 2, 2.0 and "2" are one id. Each pair of runs is compared on the items both runs hold. The report counts items that went right to wrong and items that went wrong to right, and gives the repeat floor as the share of matched items that flip. The net change alone hides flips that cancel. With three or more runs there is no combined repeat floor, you get one row per pair of runs.
  • The report lists, for each run, how many rows were left out and why, with up to 5 example ids. The reasons are an id missing, a duplicate id (every copy is left out), a missing correctness field, and a correctness value that is not true/false, 1/0, yes/no or correct/incorrect. It also lists the items present in one run of a pair and not the other. If more than 5% of a run is left out of a comparison, a warning is printed on the console and shown at the top of the report.
  • Compare two systems on the same items: python iris_check.py repeat a_run1.jsonl a_run2.jsonl --vs b_run1.jsonl b_run2.jsonl --id-field id --correct-field correct --margin 0.02 Run k of A is paired with run k of B, in the order given on the command line. Each pair gets an exact two-sided McNemar test on the discordant items and a bootstrap 95% interval for the accuracy difference A minus B. The number of matched items and the discordant counts are always printed. Both the interval and the McNemar p are used, in this order. ABOVE if the low end of the interval is above 0 and p is below 0.05. BELOW if the high end is below 0 and p is below 0.05. If only one of the two says different, CANNOT_TELL. Then CONSISTENT if the whole interval is within plus or minus the margin, but only with at least 20 matched items and at least 1 discordant item. Otherwise CANNOT_TELL. Because ABOVE and BELOW are checked before CONSISTENT, a small difference that is resolved reads ABOVE or BELOW even when it is inside the margin.
  • Read your write-up against the Faults: python -m faultsguards faults
  • Give each reading a check block before it goes in a paper or a page: check-block/. The folder you give to readcheck.py new must already exist.

Test the checker

python tests/make_synthetic.py writes a synthetic dataset where the answers are planted. These are the flips between repeats, the discordant items between systems and the parser errors. python tests/test_iris_check.py runs the checker on it and asserts that the planted answers come back.

What is here

  • iris_check.py: the sample and repeat checks, standard library only
  • START_HERE.html: this guide as a page
  • tests/: the synthetic dataset and the tests
  • faultsguards/: the Faults and Guards as a Python package, with the PDFs
  • check-block/: the check block and its commit gate
  • faultsbench/: the scorer and the planted items of our Faults and Guards bench, with the synthetic check that runs the scorer on planted worlds. Run python synth.py from inside faultsbench/. The prompts and the runner are in the repository: https://github.com/Heuremen-LLC/indahl.ai/tree/main/code/iris/faultsbench
  • parser-check/: replycheck.py regenerates replies from an lm-evaluation-harness task and writes each reply beside what each filter extracted, so the replies can be read in full. Run python replycheck.py --help for the named arguments. Output goes to --out (default ./replycheck_out). It needs pip install mlx-lm lm-eval on Apple silicon.
  • LICENSE.txt, CITATION.cff

Our other IRIS code, such as the round scorers, the training scripts and the run drivers, is in the repository at https://github.com/Heuremen-LLC/indahl.ai/tree/main/code/iris and is not copied here because it depends on our own folders and data.
