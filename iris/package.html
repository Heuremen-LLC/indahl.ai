IRIS Research Package

Heuremen LLC

Download (zip) sha256 93c207dd872d963ac3f616bbfc89f902be18903dd3a02d382ae2668549ca738d · code (git)

Cite: doi:10.5281/zenodo.23874302 (Zenodo)

Tools to check the numbers from a language-model evaluation before you trust them and after a run. This applies to benchmark scores, LLM-as-judge scores and fine-tuning studies. IRIS recounts published evaluation studies from their own released output files, and this package puts the same checks in your hands for your own outputs. Your files are opened read-only and never changed. Reports go to a separate folder, and the checker refuses a folder inside the folder that holds an input, so run it from outside your data folder. The checker sends nothing anywhere. Two parts need other software or the network when you run them: parser-check/replycheck.py runs a model on your machine, and installing the Faults and Guards package from PyPI downloads it. Python 3.9 or later.

Install the checker on its own

pip install iris-check gives the iris-check command (Python 3.9 or later): https://pypi.org/project/iris-check/

Before a run

  • Read the Guards before the work. Install the package with pip install faultsguards or from the wheel in faultsguards/, then run python -m faultsguards guards
  • Decide how each answer will be extracted from a reply and write that rule down before any reply exists.
  • If you fine-tune or compare systems, plan at least two runs of the same items with the same settings. The difference between those two runs is the repeat floor, and it is the first thing any later difference is read against.
  • Give the plan a check block: check-block/. The packs for language-model evaluations (L) and public copy (P) are in check-block/SPEC.md.

If your file holds raw replies only

iris_check.py repeat needs a correctness field for each item, so score first. A few lines of Python are enough. This one reads a JSONL file of replies and a dictionary of gold answers, and writes the {"id", "correct"} lines the checker reads. Replace the comparison with your own extraction rule. Write "correct": null for an item you did not score, and it is counted as unscored and kept out of the drop warning.

`` import json gold = {"q1": "B", "q2": "17"} # item id -> the right answer with open("replies.jsonl") as f, open("scored.jsonl", "w") as out: for line in f: r = json.loads(line) correct = r["reply"].strip().split()[-1] == gold[r["id"]] # your own extraction and comparison out.write(json.dumps({"id": r["id"], "correct": correct}) + "\n") ``

After a run

  • Save the outputs of each run as a JSONL file with one reply per line. Each line needs an item id, the reply, what your parser extracted and whether it was scored correct. Keep these files in one folder and write reports to a different folder.
  • Read a sample of replies beside what your parser extracted: python iris_check.py sample run1.jsonl --reply-field reply --extracted-field pred --label-field family --id-field id -n 10 --seed 1 This writes a reading sheet as HTML and CSV with 10 random replies per label. Read each reply. In the CSV, write x in the read column for every reply you read. In the misparsed column write x, bad, 1, wrong or misparsed where the extracted value is not the answer the reply gives. A parse that is fine takes ok, fine, 0, no, n, false or a blank. Any other entry is an error that names the row. That includes yes and y, which could mean either. Keep the sample_....json record beside the CSV. Then run python iris_check.py sample --tally SHEET.csv, which prints the result for each label and writes its report to ./heuremen_report_tally unless you give --out. The record is found by the sheet's file name, the same name ending in .json, so keep the two files together and do not rename one. If the record has another name or place, add --record sample_....json. The CSV is written as UTF-8 with a byte order mark so Excel shows accents. If you save it again from Excel, choose "CSV UTF-8". A file saved in the Windows code page is refused with that instruction.
  • The tally rule, exactly: a label reads "cannot tell (rows missing)" if the sheet holds fewer rows for it than the sample record says. Otherwise it reads "cannot tell (not read)" if any of its rows is unread. Otherwise it reads "cannot tell (parser)" when more than 10% of its read rows are mis-parsed, so 1 of 10 is fine, 2 of 10 is not, and 1 of 9 is not. Otherwise the rate can be read. The default sample is 10 replies per label.
  • Reply text that starts with =, +, - or @ gets a single quote in front of it in the CSV, so a spreadsheet does not run it as a formula. The --extracted-field should hold the extracted answer itself, not a scorer's verdict such as OK or FAULT, because the reader compares it with the reply. Items your scorer excludes by design should be set to JSON null in the extracted field, or left out of the file before you sample, so the reader is not shown them as parse failures. Rows where the reply or extracted field is absent or JSON null, blank lines, and rows with a missing or null label (shown as (none)) are counted on the console and in the JSON report. The tally takes the quote off again.
  • Count the flips between repeats of the same items: python iris_check.py repeat run1.jsonl run2.jsonl --id-field id --correct-field correct Item ids are turned into strings first, so 2, 2.0 and "2" are one id. Each pair of runs is compared on the items both runs hold. For every pair the output first gives the flip count, as flips N: right->wrong a, wrong->right b, of n matched, and then the share of matched items that flip. The share is called "flip share between these runs". It is called the "repeat floor" only when you add --repeats, which says that the runs are repeats of the same setup (same model, same settings, same machine). The net change alone hides flips that cancel. With three or more runs there is no combined figure, you get one row per pair of runs. One file should hold one model, or the model should be part of the id. If a file pools several models whose item ids repeat, give every field that makes an item unique, for example --id-field model id, and the fields are joined into one id. When repeated ids leave no matched items, the output says so in plain words and names this fix. The command exits with status 1 and says why whenever a comparison matches no items.
  • The report lists, for each run, how many rows were left out and why, with up to 5 example ids. Each row is counted once, under the first reason that applies, in this order: id missing, correctness field missing, correctness field explicitly null (unscored), correctness value not accepted, duplicate id. Unscored rows (null correct) are reported on their own and are not counted as errors in the 5% warning. A duplicate id leaves out every row that holds it, and duplicate rows and duplicate ids are counted separately. The console prints rows read = usable + the reasons. The correctness value is accepted as true or false, as the numbers 1 and 0 (1.0 and 0.0 too), or as text in any case: true, t, yes, y, correct, 1 or false, f, no, n, incorrect, 0. The report also lists the items present in one run of a pair and not the other. If more than 5% of a run is left out of a comparison, a warning is printed on the console and shown at the top of the report. It always names the count of ids not in the other run, next to the in-file reasons.
  • Compare two systems on the same items: python iris_check.py repeat a_run1.jsonl a_run2.jsonl --vs b_run1.jsonl b_run2.jsonl --id-field id --correct-field correct --margin 0.02 Run k of A is paired with run k of B, in the order given on the command line. Each pair gets an exact two-sided McNemar test on the discordant items and a bootstrap 95% interval for the accuracy difference A minus B. The number of matched items and the discordant counts are always printed. Both the interval and the McNemar p are used, in this order. ABOVE if the low end of the interval is above 0 and p is below 0.05. BELOW if the high end is below 0 and p is below 0.05. If only one of the two says different, CANNOT_TELL. Then CONSISTENT if the whole interval is within plus or minus the margin, but only with at least 20 matched items and at least 1 discordant item. Otherwise CANNOT_TELL. Because ABOVE and BELOW are checked before CONSISTENT, a small difference that is resolved reads ABOVE or BELOW even when it is inside the margin. Above 5000 matched items the interval uses count draws (two binomial draws per resample) instead of resampling items one by one. It is approximate and can differ slightly by Python version, because before Python 3.12 it uses a normal approximation. A p below 1e-300 is printed as <1e-300.
  • Read your write-up against the Faults: python -m faultsguards faults
  • Give each reading a check block before it goes in a paper or a page: check-block/. The folder you give to readcheck.py new must already exist.

Test the checker

python tests/make_synthetic.py writes a synthetic dataset where the answers are planted. These are the flips between repeats, the discordant items between systems and the parser errors. python tests/test_iris_check.py runs the checker on it and asserts that the planted answers come back.

What is here

  • iris_check.py: the sample and repeat checks, standard library only
  • START_HERE.html: this guide as a page
  • tests/: the synthetic dataset and the tests
  • TESTED.md: how the package was tested, on what, with the results, and what was not tested
  • faultsguards/: the Faults and Guards as a Python package, with the PDFs
  • check-block/: the check block and its commit gate
  • faultsbench/: the scorer and the planted items of our Faults and Guards bench, with the synthetic check that runs the scorer on planted worlds. Run python synth.py from inside faultsbench/. The prompts and the runner are in the repository: https://github.com/Heuremen-LLC/indahl.ai/tree/main/code/iris/faultsbench
  • parser-check/: replycheck.py regenerates replies from an lm-evaluation-harness task and writes each reply beside what each filter extracted, so the replies can be read in full. Run python replycheck.py --help for the named arguments. Output goes to --out (default ./replycheck_out). It needs pip install mlx-lm lm-eval on Apple silicon.
  • LICENSE.txt, CITATION.cff

Our other IRIS code, such as the round scorers, the training scripts and the run drivers, is in the repository at https://github.com/Heuremen-LLC/indahl.ai/tree/main/code/iris and is not copied here because it depends on our own folders and data.

How it was tested

This page says what was run, on what, and what came out. It also says what was not tested.

The unit tests

python tests/test_iris_check.py runs 42 tests on a synthetic dataset in tests/data/ where the answers are planted. The planted answers are the flips between repeats, the discordant items between two systems, and the parser errors. The tests check that those answers come back, and they also cover the exact test against a Fraction-based reference, a 1,000,000-item comparison, the row accounting, the tally rules, the CSV handling and the exit codes. The tests passed on Python 3.9, 3.12 and 3.14 on macOS.

A real-data test

We ran the package on our own two-machine evaluation round of 29 and 30 October 2026. That round ran FaultsBench on five open models, on a Mac and on a CUDA machine, with two same-machine repeats of each (the bare run and its exact copy). We turned the saved replies into one line per item with an id and a correct field, using the scorer from that round. Items the scorer could not read have a null correct field. The ids were joined with the model name, so the five models sit in one file per run.

The repeat command gave these flip counts. The two same-machine pairs were run with --repeats, and the two across-machine pairs were run without it, because they are not repeats of one setup. Each pair is compared on the items both runs hold.

  • Mac repeats: 1 flip, on 393 matched items
  • CUDA repeats: 4 flips, on 393 matched items
  • Mac against CUDA, bare runs: 11 flips, on 391 matched items
  • Mac against CUDA, copy runs: 10 flips, on 391 matched items

These equal the counts we published from separate code, the script item_flips.py and its output item_flips.txt, which are in the repository at https://github.com/Heuremen-LLC/indahl.ai/tree/main/code/iris/pub2/seats_compare and give flips 1, 4, 11 and 10 on the 391 items that all four runs hold. The two same-machine pairs hold 393 items each, and the 2 extra items have no flips. Both programs were written by us. So the agreement shows that the two implementations agree. It is not a check by anyone else.

The comparison command (--vs) on the Mac bare run and the CUDA bare run read CANNOT_TELL at the default margin of 0.02, with an exact two-sided McNemar p of 0.2266. The published value is 0.227.

A reading sheet on real replies

We wrote a reading sheet from real replies of the same round and a reader read 30 of them in full beside what the parser had extracted. 29 of the 30 extractions were correct. The one that was not was an item the scorer excludes by design.

What was not tested

  • Output formats of other harnesses, such as lm-evaluation-harness and HELM. The package reads a JSONL file with the fields you name, and nothing more was tried.
  • Files of more than 100,000 items on real data. The speed test with 1,000,000 items uses synthetic data.
  • Windows and Linux. The tests ran on macOS.
  • parser-check/replycheck.py runs a model, and only its --help and its argument handling are tested here.
