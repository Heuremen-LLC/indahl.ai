# Correction (30 Oct 2026, site pass H-12). Ready to append to PLAN.md and commit in one step. Not appended because the riders refuse to run while PLAN.md differs from its commit.

1. The live sensor reads asked the PurpleAir history service for a window ending at 23:59:59 of the last day. The service returns only averaging buckets that are complete inside the window (checked on 30 Oct: a day needs end at or after the next midnight, an hour needs end at or after the next hour). So each call lost its last day. The first run lost 28 Oct, and every later day was asked alone and came back empty. The code also stored an empty record for each day before asking, so a day that returned nothing was never asked again. Sensor days 28 and 29 Oct were empty from the first run on 29 Oct 18:51 UTC until 30 Oct 14:00 UTC, and the hourly strip was empty in all 17 runs. Now the window ends at the next midnight (the next hour for the strip), a day is stored only when sensors return rows, a day that returns nothing is asked again and is stored as empty after three clean runs, and PurpleAir answers are counted by kind.
2. AirNow posts the file for the newest hour part filled (4 of our 147 monitors eight minutes after the hour, 95 or more when whole). The strip takes the latest hour whose file holds at least 60 percent of our monitors, and an hour file is cached only when it holds that many. Four empty or partial hour files had been cached for good (29 Oct 22:00 and 23:00, 30 Oct 09:00 and 10:00 UTC). They were removed, read again, and the reference day of 29 Oct was recomputed.
3. The panel prints the newest sensor day and the newest AirNow day it holds beside its update time, and writes an alert line to data/last_run.log when the strip is empty in three runs in a row or the newest sensor day is more than two UTC days old.
