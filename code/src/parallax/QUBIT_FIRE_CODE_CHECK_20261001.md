## MUST FIX BEFORE FIRE
1. **Prediction file hash is recorded at fire and never checked at scoring** (C:695, 704; A:831-862, 845). Anyone can edit `predictions_*.json` after the run lands (even after seeing results), keep `_written_at` between freeze and start, and it is scored. Fix: in `score_ours` refuse unless `sha256_file(path) == metas[N]['prediction_sha256']`; better, copy the file into the chip's data folder at fire and score only that copy.
2. **Entry-level `written_at` has no upper bound** (A:853-855; C:418-421). Only the header `_written_at` is compared to the run start (A:842). Fix: require every filled entry `written_at` <= `meta['start_time']` at scoring, and <= now at fire.
3. **Reads made by fire() are logged only if the whole fire succeeds** (C:721; early exits at C:657, 662, 671, 673, 681, 693, 697, and any exception). A `--fire` without `--confirm-submit`, or a refused/failed fire, still reads the account and (for ours/maker) the chip's properties, and none of that reaches `account_reads_log.jsonl`, so the "looks taken before run 1" section (C:167-189) and the every-look-is-counted rule are not met. Fix: wrap the fire body in try/finally that calls `live.log_read`.
4. **No raw job payload is saved before parsing** (C:496-508). The real kerneled result has never been parsed by this code (the dry run substitutes synthetic I/Q; SIM BREAK in every dry-run meta). If the shape or naming differs for the middle looks, nothing is saved, recover.py fails the same way, and the fix means editing common.py, which breaks the freeze hash for scoring. Fix: write `api_client.job_results(job_id)` raw text (or the pickled PrimitiveResult) to disk before `collect_results`, outside the hashed files' control.
5. **MAKER chip is read at fire time too, and the maker number used in the report is the fire-time read, not the freeze-time prediction** (C:679, 683, 702; A:587-605 vs 799-806). Spec says the freeze-time read is the only prediction and a prediction may touch nothing but the miss column. Fix: for the maker chip use the freeze file's numbers for the report and for any display, refuse (or at least log and flag) if the fire-time calibration timestamp differs, and decide whether the maker's published T1/T2 may be printed against the measured value before the miss step (A:587-605, 696-697). The SDK's own `.target` read at submit (base_primitive.py:152) cannot be removed unless the maker chip also goes through the blind submit path; that is Wayfinder's call.
6. **BLANK chip status is fetched at submit** (SDK qiskit_runtime_service.py:1057 -> GET /backends/ibm_pittsburgh/status; allowed on purpose by L:51; plus the configuration GET at C:668). The card says nothing about the blank chip is read before or between runs, and Q5 lists status. Either Wayfinder accepts configuration + status as the unavoidable minimum and the card line is amended, or the submit has to bypass `service._run` (call `_active_api_client.program_run` directly). Code and card disagree until one is changed.
7. **Fire order and "run N-1 landed" are not enforced** (C:78, 327-334; C:651-722). Add to `fire()`: refuse unless every earlier (run, box) in FIRE_ORDER has `landed()` true, so run 2 cannot go before run 1 and the blank cannot go before ours/maker for the same run.

## NOTED
1. Server-side defaults are relied on, not pinned: dynamical decoupling, twirling (gates and measure), init_qubits are Unset (see the printed payload). Documented defaults are off / off / on. Pinning them explicitly (`enable=False`, `enable_gates=False`, `enable_measure=False`, `init_qubits=True`) removes the dependency. `init_qubits=True` with rep_delay 500 us means each shot starts from passive relaxation, not an active reset circuit.
2. The BLANK submit path was never run live. The 21:59 test reached only the configuration GET. Sources and my mock test show no properties call, but `_BlindService` pokes SDK internals (`sm._backend`, `sm._service`); it works on 0.49 only.
3. Mid-circuit measurement + kerneled: server acceptance and return shape for L2/L3 unknown until the first real job. The code refuses (loudly) anything but complex (shots, 9) arrays.
4. `max_execution_time` cap (C:349-353) is ~22 s for runs 1/2 and ~39 s for run 3 at the first job, based on the 3.0 s overhead + sequence estimate. The code's own printed worst case (3.0 s per circuit) is 32 s / 68 s. If the estimate is low the service cancels the job and nothing comes back (C:716-718).
5. SDK `usage()` substitutes 0 for a missing `usage_consumed_seconds`; and if `usage_limit_seconds` is present but null while allocation is set it raises. Guard checks only the final field.
6. `data_seen` and all `written_at` stamps are self-declared (no way for code to know). A cheap cross-check available: if an entry's `written_at` is later than an earlier run's `completed_at` in meta, require `data_seen` to include that run.
7. Freezes can be made at any time (before or after earlier runs land). If run 2/3 freezes are made after run 1 data is seen, analysis code could have been adjusted in between. Freezing all nine before the first fire closes it; nothing enforces it. Each freeze of ours/maker also re-reads the live chip (maker: calibration), so the maker chip is read at 3 freezes + 3 fires.
8. Changing analyze.py, common.py, live.py or runN.py after a run's freeze makes that run unscorable (A:821-828). Any analysis bug fix after run 1 lands therefore invalidates run 1's scoring unless it is re-frozen (and then predictions older than the new freeze are refused).
9. freeze hash does not cover freeze.py, recover.py, predictions_template.json or the other runs' runN.py (C:370-371). `run_specs` imports run1/2/3 for the budget (C:294-300).
10. recover.py needs `run{N}_pending.json` as well as the job id file (C:731). Order is derivable from the seed and real waits from dt, so a missing pending file is recoverable by hand, not by the script.
11. A freeze is not the sealed hash posted on indahl.ai: nothing in code checks that the file fired equals what was posted (hash printed at C:696 only).
12. The fire path (and recover.py) open the blank chip's arrays for shape/finite checks the moment the job returns (C:433-436, 488-491). No value is printed or analysed. If "unopened" is meant literally, validation would have to move to analysis time.
13. `predictions_template.json` / `_note` (A:552) still says "Boxes by group (OURS / MAKER / BLANK) rotate per run": stale text from before the whole-chip change. predictions_run1_ours_DRAFT.json has no `_written_at` set (correct for a draft); the template and draft have 237 identical names matching `sealable_names()`.
14. Chip assignment and blind qubit draws come from numpy `Generator.permutation` (C:48-51, 122-127). Computed now: maker ibm_phoenix, blank ibm_pittsburgh, left alone ibm_boston; blank qubits [12,26,46,103,106,108,112,141,144] if the chip has 156 qubits. A numpy change could alter them; the meta records what was used for the blank, not the assignment.
15. Environment variable `QTR_READ_LOG` (C:171, L:20) can redirect the read log silently.
16. `analyze.py` default `--data-dir` is `data/dryrun` (A:963), not `data/fire`; dry-run output is labelled SYNTHETIC in every report, but the default is easy to hit by mistake.
17. If an OFF/ON frame separation is tiny but nonzero, projected values blow up but stay finite and are not flagged; `qubit_rows` (A:475-488) flags the qubit separately but the quantity still pools it (by design: "nothing dropped").
18. Measured but not corrected, as the code itself states: each look's own readout time (about 2.2 us) is inside the "matched" elapsed wait; realized waits are 59.968 / 240.000 / 299.968 us at dt 4 ns and are recomputed from the live dt at fire (C:94-100, saved in meta).
